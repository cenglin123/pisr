# 具名失败模式与 fresh 对抗评审细则

> 本文件受 `SKILL.md` 委托，完整定义具名失败模式与 fresh 对抗评审的操作闭环；不得放宽主文件的预算、证据、重派上限或"非安全沙箱"边界。

## fresh 对抗评审：完整闭环

目的不是让多个 reviewer 复述同一结论，而是取得彼此独立的证据链。每位 reviewer 必须是新进程（`--no-session` 天然 fresh），输入仅限被审产物、审查标准和必要前置事实；不要提供其他 reviewer 的报告、verdict、未来轮次信息或汇总结论。

### 1. 布局分离

把被审产物放入只含必要输入的 staging 目录；把 reviewer 输出、轮次记录和汇总放入另一个不共享可读父树的收敛目录。不要仅靠"请勿读取"弥补可发现的 sibling 报告。每个 reviewer 使用独立输出路径和 label，避免路径碰撞。

无法物理分离时，列出所有其他 reviewer 报告、先前 verdict、未来轮次材料和收敛工作目录，作为禁读路径；这只是 best-effort 协作约束，既不是访问控制，也不构成安全沙箱。

### 2. 禁读与 prompt 合同

在自足 prompt 中同时写明：

- 允许读取的绝对路径清单，以及"其他位置一律禁读"；
- 禁止读取的绝对路径清单，尤其其他 reviewer 产物、verdict 和未来轮次信息；
- 不得引用、复述或据此趋同；
- 输出执行证据必须含结构化 `reads:` 列表，逐行给出实际读取的绝对路径；
- 唯一绝对输出路径，以及写错路径可能覆盖他人产物的后果。

使用驱动器的 `--forbid-paths <path>` 为每个禁读根路径注入 prompt 副本；原 prompt 不改。它会在产物落盘后将 `reads:` 与禁读路径比较（Windows 路径大小写不敏感且子路径命中），记录 `clean`、`violated(<path>)` 或 `unavailable`。`unavailable` 不是 clean：补充人工审计或把报告视为无法证明独立性。

reviewer 通道应同时使用 `--tools read,grep,find,ls`（进程级只读白名单）：即使 `reads:` 审计被绕过，写入与命令执行在工具面仍不可达，把污染面压缩到只剩"读了不该读的"。

### 3. 审计与裁定

审计"是否不该访问"的准则如下：

- **不该访问**：提前获取答案（提前看到产物本身或其他 reviewer verdict），或作弊性质的信息（未来轮次材料、绕过任务边界）。
- **允许的任务信息**：为完成审查所必需、非作弊的前置文件、规范和先例。

对每份报告检查 `reads:`、引用路径和 findings。若发现禁读或不该访问：默认**作废该 verdict**，保留现场和审计证据，以新进程、隔离布局、修订后的 prompt 重派；重派仍受 `SKILL.md` 的三次总尝试和幂等限制。不得把补充解释包装成 fresh 复评（pi 一次性派发无"同一会话"概念，此风险主要来自复用同一 prompt 上下文）。

唯一例外是能留下可核验证据证明实质独立性仍保留：findings 与被读报告零重叠，且该 reviewer 独立否定过被读报告的错误。此时可降级保留，并在汇总中如实标注越界、证据和降级理由；不能证明即作废重派。

## 锚定污染

- **症状**：reviewer 引用、复述或无独立证据地趋同于并行/前轮结论。
- **根因**：共享可读父树、prompt 仅列必读不列禁读、或把整个工作目录给成输入。
- **对治**：严格执行上节布局分离、禁读合同、`reads:` 审计与作废/重派；叠加只读工具面。

## 越界写入 / 路径碰撞

**指纹**：进程 exit=0、期望产物未落盘，却在别处写入内容；这既非静默停滞也非 0 产物报告幻觉，且可能覆盖其他 agent 的成果。

**根因**：`--output-pattern` 只供 watcher 等待，不约束子代理写入；含占位符的输出路径会让模型自行命名。

**对治**：prompt 的输出节写死唯一绝对路径、禁止占位符并说明覆盖后果；派发前备份输出目录既有产物；用驱动器的前后快照比对，发现覆盖即报错并保留证据。不要只把"缺少期望文件"当普通重派而掩盖损失。另见 dispatch-patterns.md §退出码契约的 `exit_0_no_artifact` / `exit_0_name_mismatch` 分层。

## 只读工具面下的写入请求

**指纹**：`--tools read,grep,find,ls` 派发的 reviewer 被要求（或自作主张）产出文件时，模型回复"我没有 write 工具"，进程 exit=0 且零产物。本机 pi 0.84.3 实证：模型明确感知工具缺失并拒绝，不产生越权写入。

**对治**：这不是失败模式而是白名单生效的证据；但若你的验收本就期望文件产物，说明工具面配置错了——产物型 worker 不要加只读白名单。判定时先核对本次派发的工具面声明（prompt 第七要素）。

## 看门狗误杀

大任务可能在产物基本完成、仅差收尾时被常规阈值杀掉。按预估产出量调整阈值（大规模单任务可为 60 分钟），再按失败切换阶梯补交缺失产物；不要无证据地重跑整个任务。
